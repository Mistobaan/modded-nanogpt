Memory Optimizations

Activation Checkpointing Per Block (train_gpt.py:423-444) Current: all 12 blocks run without checkpointing, so activations for 48k tokens stay resident (~5‑6 GB just for block outputs) and limit usable batch/window; Performance Impact: high HBM pressure, earlier eviction of compilations and smaller workspace for kernels; Optimized Solution: wrap mid/late blocks with torch.utils.checkpoint.checkpoint(block_forward, use_reentrant=False) while keeping first/last couple full precision for stability—pairs well with CUDA graphs as shapes stay fixed; Expected Improvement: ≈35‑40% activation-memory reduction enabling +1 block mask tier or larger context; Implementation Priority: High.
Lazy Value Embeddings (train_gpt.py:412-420) Current: ve = [value_embed(input_seq) ...] materializes three full-length tensors (≈210 MB bf16) every forward even though only six layers need them; Performance Impact: pushes peak memory and hurts compile caching; Optimized Solution: compute embeddings on demand (e.g., store closures or lightweight cache keyed by layer id), optionally checkpoint the recomputation to trade a tiny matmul for big memory savings; Expected Improvement: ~200 MB lower footprint and better allocator stability, negligible compute cost; Implementation Priority: Medium.
Pre-shard BOS Boundaries (train_gpt.py:522-534) Current: find_batch_starts scans max_batch_span with torch.nonzero each batch, creating temporary CPU tensors; Performance Impact: ~100 k-element scans per step plus pinned memory churn; Optimized Solution: cache BOS indices once per shard during _load_data_shard (store in Tensor on CPU) and serve batches via pointer arithmetic; Expected Improvement: frees ~150 MB/s of CPU memory traffic and trims ~2% host time, making room for bigger activation buffers; Implementation Priority: Medium.

Extend FP8 Coverage (train_gpt.py:304-377) Current: FP8 matmul is only enabled for lm_head, leaving MLP and attention projections in bf16; Performance Impact: linear layers dominate FLOPs, so bandwidth-bound bf16 GEMMs limit Tensor Core throughput; Optimized Solution: integrate Transformer Engine tensor parallel modules or enable use_fp8=True for c_fc, c_proj, and attention projections with per-layer scaling + master fp32 weights; Expected Improvement: 12‑18% faster matmuls and ~25% activation bandwidth reduction once calibrated; Implementation Priority: Medium.
Fuse Muon Orthogonalization (train_gpt.py:170-205) Current: Newton–Schulz runs as multiple GEMMs per parameter via eager PyTorch; Performance Impact: ~6% step time in GEMM/launch overhead; Optimized Solution: author a batched Triton kernel (or use torch.compile(..., mode="reduce-overhead") with ATen fusion) that computes A, B, and update in one kernel; Expected Improvement: 4‑6% faster optimizer step; Implementation Priority: Medium.
Scaling Optimizations

Bucketed Reduce-Scatter/All-Gather (train_gpt.py:170-205,212-246) Current: both Muon and DistAdam iterate parameters and issue dozens of small collectives, each with fresh temporary buffers; Performance Impact: NVLink throughput falls to ~45‑55% of peak and adds >10% wall time; Optimized Solution: build contiguous buckets per dtype/size, pre-allocate reduce-scatter and all-gather workspaces, launch one reduce_scatter_tensor/all_gather_into_tensor per bucket, and overlap the gather of bucket n with compute of bucket n+1; Expected Improvement: 8‑12% end-to-end speedup with better comm/compute overlap; Implementation Priority: High.
Overlap Gradient Communication with Backward (train_gpt.py:733-744) Current: collectives fire only after loss.backward() finishes, so no overlap with tail layers; Performance Impact: idle 0.3‑0.4 ms per layer on 8×H100; Optimized Solution: register autograd hooks (e.g., torch.distributed.algorithms.ddp_comm_hooks.post_localSGD_hook) or use TorchCompile’s ddp_graph to trigger reduce-scatters as soon as gradient bucket is ready; Expected Improvement: 5‑7% shorter iteration; Implementation Priority: Medium.
Validation Offload (train_gpt.py:700-718) Current: validation uses full model replicas on all ranks, blocking training and doubling HBM use; Performance Impact: several seconds of idle compute per eval; Optimized Solution: dedicate two ranks to validation with dist.new_group or stream validation on CPU/off-GPU ranks while others keep training (staggered eval); Expected Improvement: hides most of validation cost, net 3‑4% throughput gain over full run; Implementation Priority: Low.
